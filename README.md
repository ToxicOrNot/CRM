# Локальная CRM

Локальная CRM-система для небольшой компании. Сейчас система закрывает два базовых процесса: постановку задач и учет заказов, который заменяет текущую Excel-таблицу. Полноценная клиентская база пока не реализована, поэтому контакты клиента хранятся непосредственно в заказе.

## Стек

- Python 3.12+
- Django 5.2 LTS
- PostgreSQL
- Django Templates
- Bootstrap 5
- Docker Compose
- Django TestCase

## Требования

- Docker и Docker Compose
- Git
- Для локального запуска без Docker: Python 3.12+ и PostgreSQL или SQLite для быстрой проверки

## Быстрый запуск через Docker Compose

Создайте локальный файл окружения:

```powershell
copy .env.example .env
```

Запустите сервисы:

```powershell
docker compose up --build
```

Приложение будет доступно по адресу:

```text
http://localhost:8000/
```

Контейнер `web` перед запуском ожидает готовности PostgreSQL и применяет миграции автоматически.

## Миграции

Применить миграции вручную:

```powershell
docker compose exec web python manage.py migrate
```

Проверить, что модели соответствуют миграциям:

```powershell
docker compose exec web python manage.py makemigrations --check --dry-run
```

## Суперпользователь

Создать администратора:

```powershell
docker compose exec web python manage.py createsuperuser
```

Пользователи CRM создаются через Django Admin:

```text
http://localhost:8000/admin/
```

## Тесты

Запуск тестов в Docker:

```powershell
docker compose exec web python manage.py test
```

Быстрый локальный запуск тестов на SQLite:

```powershell
$env:DJANGO_USE_SQLITE='1'; .\.venv\Scripts\python.exe manage.py test
```

## Модуль задач

Реализовано:

- собственная модель пользователя `accounts.User` на основе `AbstractUser`;
- поля пользователя `position` и `department`;
- модель `Task` со статусами и приоритетами через `TextChoices`;
- автоматическое заполнение постановщика задачи текущим пользователем;
- автоматическое управление `completed_at` и архивированием при отметке «Выполнена»;
- общий список задач, «Мои задачи» и архив задач;
- создание, просмотр и редактирование задач;
- разворачивание карточки задачи прямо в списке;
- прикрепление файлов к задачам и скачивание всех файлов одним ZIP-архивом;
- права редактирования задачи: постановщик, исполнитель или суперпользователь;
- фильтры и сортировка списка задач;
- связь задачи с заказом через необязательное поле `Task.order`.

## Модуль заказов

Модель `Order` содержит:

- `order_date` — дата заказа;
- `delivery_date` — дата выдачи, автоматически заполняется при переводе заказа в статус `DELIVERED`;
- `status` — статус заказа;
- `order_number` — номер заказа, допускает пустое значение и повторы из старой Excel-таблицы;
- `work_information` — информация о работе;
- `contacts` — контактные данные клиента в свободной форме;
- `total_amount` — сумма к оплате;
- `advance_amount` — аванс;
- `additional_payment` — доплата;
- `comment` — комментарий;
- `created_by`, `created_at`, `updated_at`;
- `archived` — архивный признак.

Статусы заказа:

- `ACCEPTED` — Новый;
- `WAITING_RESPONSE` — Ожидаем ответ/предоплату;
- `IN_PROGRESS` — В работе;
- `READY` — Позвонили о готовности;
- `DELIVERED` — Заказ отдан;
- `CANCELLED` — Отменен.

Финансовый расчет:

```text
Остаток = Сумма к оплате - Аванс - Доплата
```

Остаток не хранится в базе данных, а вычисляется свойством `Order.balance`. Денежные поля используют `DecimalField`, отрицательные значения запрещены, аванс и доплата вместе не могут превышать сумму заказа.

В интерфейсе заказов реализовано:

- список активных заказов;
- создание и редактирование заказов;
- разворачивание заказа прямо в списке кликом по строке;
- быстрое изменение статуса, суммы, аванса и доплаты из раскрытой строки заказа;
- карточка заказа с блоками информации, финансов, комментария, связанных задач и служебных данных;
- поиск по номеру заказа, информации о работе, контактам и комментарию;
- фильтры по статусу, датам, просрочке, оплате и остатку;
- сортировка по дате заказа, дате выдачи, сумме и остатку;
- архив заказов без физического удаления;
- восстановление заказа из архива;
- кнопка «Создать задачу для заказа» с предзаполненной связью с заказом.

Импорт старой Excel-таблицы:

```powershell
docker compose exec web python manage.py import_orders_xlsx "заказы 2025 — копия.xlsx" --dry-run
docker compose exec web python manage.py import_orders_xlsx "заказы 2025 — копия.xlsx" --created-by admin
docker compose exec web python manage.py import_orders_xlsx "заказы 2025 — копия.xlsx" --created-by admin --last 10
```

`--dry-run` показывает сводку без записи в базу. При импорте:

- статус берется из текстовой колонки, а если она пустая — из цвета строки Excel;
- Excel-статус «Заказ создан» импортируется как CRM-статус «В работе»;
- поле «где печатаем» и дополнительные пометки из правых колонок сохраняются в комментарий заказа;
- некорректные денежные значения не останавливают импорт, а заносятся в комментарий как предупреждения;
- если в Excel аванс и доплата больше суммы заказа, сумма к оплате поднимается до суммы платежей, чтобы в CRM не появлялся отрицательный остаток;
- дата выдачи переносится только для заказов со статусом «Заказ отдан» и не переносится, если она раньше даты заказа;
- пустые даты заказа наследуются от предыдущей заполненной строки таблицы.

## Права доступа к заказам

Модуль заказов использует стандартные Django permissions:

- `orders.view_order` — просмотр списка и карточки;
- `orders.add_order` — создание;
- `orders.change_order` — редактирование, архивирование и восстановление;
- суперпользователь имеет полный доступ.

Права назначаются через Django Admin. Отдельная ролевая модель для заказов пока не создавалась.

## Файлы задач в локальной сети

Файлы задач хранятся в локальной папке `media/` и доступны по URL вида:

```text
http://IP_СЕРВЕРА:8000/media/tasks/...
```

Для доступа с других ПК в локальной сети:

- запускайте приложение через Docker Compose, где Django слушает `0.0.0.0:8000`;
- откройте порт `8000` в firewall сервера;
- в `.env` оставьте `DJANGO_DEBUG=1` для локального dev-сервера;
- в `DJANGO_ALLOWED_HOSTS` укажите IP сервера или `*` для внутренней сети.

Для постоянной эксплуатации лучше отдавать `/media/` через Nginx или другой веб-сервер, а Django оставить только для приложения.

## Намеренно не реализовано

- полноценная клиентская база;
- отдельная модель контактов;
- платежные транзакции, касса и бухгалтерский учет;
- интеграция с банком;
- автоматическое формирование документов;
- SMS и Telegram-уведомления;
- файлы заказа;
- история всех изменений;
- отчеты по прибыли;
- складской учет;
- сложные производственные маршруты;
- Kanban;
- REST API;
- SPA на React, Vue или аналогичных фреймворках;
- публичная регистрация пользователей;
- физическое удаление задач и заказов через пользовательский интерфейс.
